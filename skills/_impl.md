# 対応スキル（impl）

このセッションでは課題の【実装】を行います。ブランチは切らず**既定ブランチ（main/master）上で直接**実装→検証→**ローカルコミット**まで行い、issue に `AI:impl-done` ラベルを付与して処理済みフラグを立てます。**push・PR作成・ブランチ作成は禁止**（リモートへの反映は別セッションの再検証が行う）。以下の制約を必ず守ってください。

## フォールバックを極力作らない

- 要件に対する本命の実装を1本で作る。「失敗したら別経路でごまかす」代替実装・サイレントフォールバックは追加しない
- 例外や取得失敗を握りつぶして別値・別処理で継続させない。失敗はエラーとして表面化させる
- 「本当は動いていないが見かけ上成功する」経路を残さない

## ポーリングを極力しない

- `sleep` + ループで定期的に状態を確認する実装を新設しない
- 待機が必要な場合はイベント駆動を使う（イベント/コールバック/ファイル監視/フック/通知）
- やむを得ず待つ場合も一回確認＋明確なタイムアウトに留め、周期的ポーリングを追加しない

## 周期的に動作するロジックを極力入れない

- タイマー・定期実行（`setInterval`/cron/常駐ループ等）で自動的に繰り返し動く処理を新設しない
- 処理はイベント発生時・呼び出し時に実行する設計にする
- 定期実行が要件そのものである場合のみ採用し、実行間隔と停止条件を明確にする

## 動作が異常に遅くなるロジックを採用しない

- データ量に対して非現実的な計算量になる実装（大きなデータへの全件二重ループ・逐件リモート呼出し等）を採用しない
- ビジーウェイト（空ループで時間を潰す）・無駄な全件走査・全ファイル再読込みを新設しない。差分・絞り込み・必要分のみの取得で済ませる
- 既存処理を明らかに遅くする変更は避け、やむを得ず性能が悪化する場合は理由と影響範囲をコミットメッセージと issue コメントに明記する

## 完了確認（必須）

- 完了を宣言する前に、**必ず完了時スキル（`_done`）の確認項目をすべて実施**し、動作確認の証拠（実行したコマンド・確認した画面・連携先での受信確認）を issue コメントまたは最終報告に明記する
- 環境制約で確認できなかった項目は「未確認」として明記し、`needs-review` 相当として扱う。未確認のまま完了を装わない
- 確認が NG の場合は、修正→再確認のループをプロンプトに指定された上限回数まで繰り返す。上限に達しても完了しない場合は、このセッションで自分が作成したコミット（末尾 `Issue: #N` トレーラー付き）を `git revert --no-edit` で除去し、`git push` で除去をリモートへ反映してから「対応困難」として理由と現状を issue コメントで報告し、issue をクローズして終了する（この push は断念時の除去目的のみ許可。push が拒否・revert が衝突した場合は除去せずその旨を報告。`AI:impl-done` を既に付けていた場合は除去する。未コミットの作業ツリー変更は消さないが、残った旨をコメントに明記する）
- 検証 OK なら変更を**ローカルコミット**し（コミットはこの課題の変更のみ含める）、issue に `AI:impl-done` ラベルを付与して処理済みフラグを立てる。**push はしない**——push は再検証と一体の仕事として verify セッションのみが行う（例外は断念時の除去目的のみ）。push された変更は全課題分がまとめて公開されるため、再検証を通っていないコミットをリモートへ出してはいけない
- コミットメッセージ末尾に Issue: #N トレーラーを必ず付ける（N は対象課題番号。verify の帰属判定に使用。(#N) 表記も従来互換で解釈されるが末尾トレーラーを優先する）

## 破壊的な改良は行わない

- 課題の解決に必要な最小差分に留める。動いている既存コードの削除・大規模リファクタ・リネーム・構造再編を行わない
- 既存の公開 API・CLI・ファイル形式・DB スキーマの後方互換を壊さない
- push・force push・ブランチ作成・PR 作成・既存データの削除は明示許可がない限り禁止

## セキュリティを重視する

- 秘密情報（トークン・鍵・パスワード）をコード・コミット・ログに入れない
- **公開データに API キー・個人情報が入っていないか確認する**。コミット対象ファイル・issue/PR コメント・生成物（スクリーンショット・ログ・出力ファイル）に、API キー・トークン・認証情報・個人情報（氏名・住所・メール等）が混入していないか push/公開前に確認する
- 外部入力は検証し、コマンド/SQL/パス等のインジェクション対策を行う。権限は最小限にする
- 無検証の `eval`/`exec`、安全でないデシリアライズ等の危険パターンを新設しない
- pre-commit 等のセキュリティ制御（detect-secrets/bandit/audit）を緩めたり迂回したりしない

## 外部プログラム・依存のライセンス

- 依存追加・外部ツール/ライブラリ導入の前にライセンスを必ず確認する
- **商用利用を禁止するライセンスは使用しない**（CC-BY-NC 系・"non-commercial use only"・独自の商用制限等）
- copyleft（GPL/AGPL/SSPL 等）はリポジトリのライセンス方針に適合すると確認できる場合のみ採用し、判断できない場合は採用しない
- 新規依存は安定版を固定バージョンで追加し、`latest` 等の浮動指定は避ける
- **追加した依存・利用した外部プログラムのライセンス名を issue コメントに明示する**
