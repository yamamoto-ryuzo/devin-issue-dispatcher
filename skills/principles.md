# 解決原理カタログ（principles.md）

繰り返し現れる課題の型に対し「**どの条件でどの解決部品を、何と併用して選ぶか**」を置く原理カタログ。
形式は taxonomy §9（解決原理）を借用する。原理は辞書の型（原因の仕組み）とは別の層で、
**解決の側だけ**を持つ。

- impl セッションは**実装の前に**本書を読み、課題の型に当たる原理があれば部品・派生形を選んで適用する
- **点数による自動選択は作らない**——読んで当てるのはエージェント。人が触るのは、当てた原理が
  効かなかった・誤適用だった・記述が間違っていたと問題が明らかになったときだけ

## 原理の形式

各原理は `#### <slug>` 見出しと次の欄を持つ:

| 欄 | 意味 |
|---|---|
| 守る条件 | 不変条項・原則。原理は「原則 X を仕組み M の下で守る手段」 |
| 破られる条件 | どの状況・仕組みで破られるか。独立に破る要因は分けて書く |
| 当たる型 | 課題座標の型（原因の仕組み。1 原理が複数の型に当たってよい） |
| 併用する部品 | **補完**関係の部品。「どれか 1 つでは何が残るか」を根拠付きで書く |
| 派生形と選択条件 | **選択**関係の派生形と、どれを選ぶかの条件 |
| 非適用 | 当てない場合（当てると責務の二重化・対象の混同になる場合を含む） |
| 反例 | 部品ごとの確かめ方（見逃しやすい誤適用の形） |
| 正本 | 部品を実装した正本モジュール・設計書・規約 |

## 適用の記録（`principles` 欄）

impl セッションの出力に `principles` 欄を持たせる（`_impl.md` の指示を参照）:

- `use: consulted` = 実装前に原理を読んで部品・派生形を選んだ（前向きの適用）
- `use: extracted` = 直した後に後付けで対応付けた（成立には数えない）
- `note` = 採った部品・派生形と、その事例に固有の差分

ナレッジ記録（#103 の JSON）では `resolution.principles` に
`{principle: <slug>, use: consulted|extracted, note: ...}` を書く。

## 成立・撤退

- **成立**: `use: consulted` の実績が**別々の型**から 2 件以上あり、かつそのどれについても
  **適用後に同型の見逃し**が無いこと。`extracted` は成立に数えない
- **撤退**: `consulted` が現れない原理は統合か廃止する。参照した事例と `note` は残す（情報を落とさない）
- **参照する事例の無い原理は置かない**。欄に機能名・ファイル名の羅列を書かない（正本欄を除く）

## 原理

#### route-all-surfaces-through-one-point

- **守る条件**: 状態を変えたら、その状態が表示に使われる全箇所へ即時反映する（状態と画面の乖離は障害）
- **破られる条件**: 実行経路が複数（直接起動・チャット・委譲・手動）あるのに、表示が一部経路の
  フラグだけを見て残りの経路が抜け落ちる。反映経路が複数に分かれ、一方だけ更新される
- **当たる型**: 状態と画面の乖離。同型の是正を面（経路・表示箇所）ごとに塞いで再発する型
- **併用する部品**: 「全経路が通る 1 箇所への集約」＋「即時反映の横断検査」。集約だけでは
  反映タイミングの穴が残り、即時反映だけでは経路の抜けが残る
- **派生形と選択条件**: プッシュ配信（ファイル監視→イベント通知）= 状態が常時変わり購読者がいる時 /
  アクション起点の再読込 = ユーザー操作・取得のタイミングで追従できれば足りる時
- **非適用**: 表示を持たないバッチ処理、実行経路が 1 つしかない処理
- **反例**: 1 経路で反映されることだけ確認して他経路を未検証で放置する。「実行中」表示が
  一部経路のフラグだけを見ている
- **正本**: `AGENTS.md`「状態変更は必ず UI へ反映する」、control.mjs の `fs.watch`→SSE 配信、
  task-prompts.mjs（プロンプト生成の 1 箇所化）

#### verify-then-publish-or-revert

- **守る条件**: 検証を通っていないコミットはリモートへ公開しない。公開は再検証と一体の仕事
- **破られる条件**: 実装と push が別セッションに分かれ、断念済み・差し戻し済み・帰属不明の
  コミットが未 push のまま滞留し、次の一括 push でまとめて公開される
- **当たる型**: 未検証作業の公開、断念・失敗作業の残留（除去がローカルに閉じてリモートに残る）
- **併用する部品**: 「帰属判定（コミット末尾 `Issue: #N` トレーラー）」＋「`git revert` による
  除去」＋「除去の `git push` 反映」。帰属だけでは除去すべき対象が分からず、revert だけでは
  除去がリモートへ反映されず滞留が解消しない
- **派生形と選択条件**: 一括 push = 全未 push コミットが open の監視課題に帰属する時 /
  個別 revert＋push = 帰属不明・closed/rejected・needs-review/failed の課題のコミットが混在する時
- **非適用**: 公開先（リモート）を持たない作業
- **反例**: revert したが push していない（除去が反映されず、差し戻し後の impl が未 push ゲートで
  起動しない）。`git reset` で消す（他課題の未検証コミットを破壊する）
- **正本**: `AGENTS.md`「処理ライフサイクル（verify の混在ルール）」、`skills/_pr.md`
