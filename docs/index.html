課題エージェント ディスパッチャー — システムドキュメント

GitHub Issue/PR を監視し、Devin エージェント（devin -p / ACP チャット）が課題の評価・実装・PR対応を自動で行う常駐システム。管理パネル http://127.0.0.1:8585 から全体を制御する。

目次: 構成 · 全体フロー · 委譲ライフサイクル · 管理パネル · スキル · 4段階判定 · 設定項目 · 他IDE連携 · 安全設計

委譲チャット実行（chatDelegated）のライフサイクル

impl/verify を devin -p 単発セッションではなく ACP チャットセッションへ委譲する経路。投入は2系統ある: ① dispatcher の runTask が非 devin エンジン解決時に POST /api/chat/task 経由で委譲（devin:running ラベル付き）、② control 側の自動連鎖（評価 verdict → chatWait → dispatchChatTask。こちらはラベルを付けない）。

#隙間原因
G1ch.busy が解消しないsession/prompt の応答も turn_complete も来ずプロセスも生存 → busy を false にする経路が無い（acp-chat.mjs 側にターン上限が無い）
G2watcher が再起動で消えるimplWatchers はインメモリ。restoreChats はチャットを復元するが watcher は再アームされず、委譲中タスクが孤立する
G3timeout が終端化しないrecordWatchTimeout は inflight 系のみ解除。chatDelegated/delegatedAt/chatId/status='running' を残す（!t?.inflight 早期 return もあり）
G4stale 回収が届かないreclaimStale は devin:running ラベル走査のみ。自動連鎖（chatWait）経路はこのラベルを付けないため対象外

層機構配置効果
L0busy 停滞検知＋強制 turn 終了（無応答 chatStallMinutes 分で session/cancel→proc kill → busy=false）acp-chat.mjs send() / onUpdate / checkStall根本原因を塞ぎ、通常経路で chatResult へ到達させる
L1awatcher timeout を「マーカー掃除」から「終端解決」へ: gh のフラグ/close 状態を確認し chatResult{via:'watch-timeout'} を書く。失敗時は needs-review＋engineError。併せて滞留セッションを cancelcontrol.mjs recordWatchTimeout30分で必ず終端状態へ遷移。dispatcher の既存消費（ラベル適用・verify-ng エスカレーション）をそのまま通る
L1b起動時に chatDelegated 残存タスクを走査し watcher 再アーム or 即終端解決control.mjs 起動シーケンス（restoreChats 後）control 再起動による孤立を解消
L2chatDelegated＋delegatedAt 超過＋chatResult 無しを dispatcher が自前で gh 確認→終端化dispatcher.mjs reclaimStale 拡張 or 別 sweepcontrol 全停止時の最終セーフティネット。閾値は L1(30分)より長く設定し二重解決を避ける
補助パネルに委譲経過時間＋滞留警告を表示panel.html / /api/candidates人間が気づけるようにする（表示用フィールドは API 応答へ含める規約に従う）
設計上の要点: 終端化は「マーカーを消す」ではなく「chatResult を書く」で行う。これにより status 確定・ラベル適用・verify-ng エスカレーションが全て dispatcher の既存消費経路（syncShared）に一本化され、二重状態遷移を防げる。観測例では作業自体は完了し AI:impl-done も付与済みだったため、いずれの層が機能していても impl-done 終端へ正しく落ちていた。

work-queue プロトコル（pull 型の実行契約）

投入された課題は work-queue.json に以下の形で蓄積される:

{
  "key": "owner/repo issue#N",       // 課題キー（一意）
  "mode": "impl" | "assess",          // impl=実装 / assess=評価のみ
  "repo": { "github": "owner/repo", "path": "C:\\devin\\..." },
  "type": "issue" | "pr",
  "number": 65, "title": "...", "url": "...", "body": "...",
  "status": "pending" | "in-progress",
  "queuedAt": "ISO8601", "claimedAt": "ISO8601"
}

エージェント側の手順:

  1. queue_list で pending 一覧を取得
  2. queue_claim({key}) — status が in-progress になり {task, instructions} が返る（instructions に作業手順・リポジトリ指針・禁止事項を同梱。claim した側が instructions に従うことが契約の本体）
  3. 指示に従い実行。impl は既定ブランチでローカルコミット＋ AI:impl-done ラベル付与まで（push・PR・ブランチ作成は禁止。リモート反映は別経路の再検証が行う）
  4. queue_done({key, status, note}) で完了記録。status = done / failed / needs-review。assess 課題は note に {"category":..,"risk":..,"reason":..} 形式の JSON を入れると判定として state.json に記録される

完了時はキューから除去され state.json の tasks[key] に {status, note, finishedAt, engine:"ide"}（assess は判定も）が記録される。注意: in-progress のまま放棄された項目は pending へ自動復帰しない（現状は手動で再投入）。

安全設計

  • 二段階の検証ゲート: 実装セッションはローカルコミットまで（push は断念時の revert 除去のみ許可）。リモートへの push は別視点の再検証を通ったコミットのみ。未検証コミットが残るリポジトリでは新規実装を開始しない（混入 push 防止）
  • CSRF 対策: POST は X-Panel: 1 ヘッダ必須・127.0.0.1 バインドのみ
  • レース対策: state.json の原子的リネーム・children.json の flock による多重起動防止
  • 検証ループ有界: 実装↔検証のループは implLoopMax で打ち止め、対応困難は issue コメントでユーザーへ報告
  • 禁止事項: フォールバック乱用・不必要なポーリング/定期実行・低速ロジック・破壊的操作をスキルで禁止
  • 証拠主義: 「完了」は動作確認＋スクリーンショット等の証拠がある場合のみ
  • 公開データの機密チェック: コミット・コメント・生成物に API キー/個人情報を入れない（`_impl`）
運用メモ: control.mjs は常駐プロセスのため、コード変更は再起動が必要（/api/reload は config.json のみ再読込）。goals.json・work-queue.json 等の実行時データは .gitignore 済み。
