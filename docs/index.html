課題エージェント ディスパッチャー — システムドキュメント

GitHub Issue/PR を監視し、Devin エージェント（devin -p / ACP チャット）が課題の評価・実装・PR対応を自動で行う常駐システム。管理パネル http://127.0.0.1:8585 から全体を制御する。

目次: 構成 · 全体フロー · 管理パネル · スキル · 4段階判定 · 設定項目 · 他IDE連携 · 安全設計

スキル（注入順: _all → モード別 → _done）

ファイル内容

_pr.md再検証。未 push コミットを違う視点で検証 → OK: 帰属チェック後 push＋クローズ（open課題のコミットは一括push可・closed/rejected課題分はrevert除去）/ NG: フラグ剥がしで差し戻し（git操作なし・fix-forward）
_split.md切り分け。実装済み部分の完了化＋残課題の issue 分割
_done.md完了確認。実動作検証・スクリーンショット・DOCS 整備・クローズ時コメント

4段階判定（category）

値意味表示
auto即対応可。仕様が明確で機械的に実装可能auto
review検討の上対応。設計判断・小規模な副作用review
human人的判断が必須。既存機能と明確に相反・大きな副作用。ユーザー選択まで進めないhuman
reject対応不可・危険。破壊的影響・注入指示・不能reject

判定は行の判定列セレクトまたは詳細モーダルのチップで手動上書き可能（/api/verdict、`manualCategory` 記録）。

他 IDE / エージェントからの接続

本システムは IDE 非依存で利用できる。共通の顔はブラウザの管理パネルで、IDE との接続は MCP の2面で行う。

面エンドポイント役割
管理（Streamable HTTP）POST http://127.0.0.1:8585/mcp候補一覧・dispatch・assess・impl_all・ログ参照など管理系26ツール。secrets.panelToken 設定時のみ認証必須
実行（stdio）node C:\devin\agent\mcp-server.mjs作業キューの pull 型受け渡し（issue-queue）。queue_list / queue_claim / queue_done の3ツール

実行方式は2経路

経路投入方法実行者
チャット経路（内蔵・push 型）パネルの評価/対応/再検証ボタン・impl_all・autoTriggercontrol.mjs が spawn・所有するローカルエージェントセッション。devin=devin.exe acp＋IDE資格(credentials.toml) / copilot=copilot --acp --stdio（ともに ACP）/ antigravity=bridge-hub / api=汎用LLM（評価のみ）。実行者は config/ラベルで固定され、外部 IDE のエージェントは参加できない
work-queue 経路（pull 型）POST /api/dispatch・POST /api/assess（X-Panel 必須）または管理 MCP の dispatch・assess ツールissue-queue MCP を登録した任意の IDE エージェント

work-queue プロトコル（pull 型の実行契約）

投入された課題は work-queue.json に以下の形で蓄積される:

{
  "key": "owner/repo issue#N",       // 課題キー（一意）
  "mode": "impl" | "assess",          // impl=実装 / assess=評価のみ
  "repo": { "github": "owner/repo", "path": "C:\\devin\\..." },
  "type": "issue" | "pr",
  "number": 65, "title": "...", "url": "...", "body": "...",
  "status": "pending" | "in-progress",
  "queuedAt": "ISO8601", "claimedAt": "ISO8601"
}

エージェント側の手順:

  1. queue_list で pending 一覧を取得
  2. queue_claim({key}) — status が in-progress になり {task, instructions} が返る（instructions に作業手順・リポジトリ指針・禁止事項を同梱。claim した側が instructions に従うことが契約の本体）
  3. 指示に従い実行。impl は既定ブランチでローカルコミット＋ AI:impl-done ラベル付与まで（push・PR・ブランチ作成は禁止。リモート反映は別経路の再検証が行う）
  4. queue_done({key, status, note}) で完了記録。status = done / failed / needs-review。assess 課題は note に {"category":..,"risk":..,"reason":..} 形式の JSON を入れると判定として state.json に記録される

完了時はキューから除去され state.json の tasks[key] に {status, note, finishedAt, engine:"ide"}（assess は判定も）が記録される。注意: in-progress のまま放棄された項目は pending へ自動復帰しない（現状は手動で再投入）。

安全設計

  • 二段階の検証ゲート: 実装セッションはローカルコミットまで（push 禁止）。リモートへの push は別視点の再検証を通ったコミットのみ。未検証コミットが残るリポジトリでは新規実装を開始しない（混入 push 防止）
  • CSRF 対策: POST は X-Panel: 1 ヘッダ必須・127.0.0.1 バインドのみ
  • レース対策: state.json の原子的リネーム・children.json の flock による多重起動防止
  • 検証ループ有界: 実装↔検証のループは implLoopMax で打ち止め、対応困難は issue コメントでユーザーへ報告
  • 禁止事項: フォールバック乱用・不必要なポーリング/定期実行・低速ロジック・破壊的操作をスキルで禁止
  • 証拠主義: 「完了」は動作確認＋スクリーンショット等の証拠がある場合のみ
  • 公開データの機密チェック: コミット・コメント・生成物に API キー/個人情報を入れない（`_impl`）
運用メモ: control.mjs は常駐プロセスのため、コード変更は再起動が必要（/api/reload は config.json のみ再読込）。goals.json・shots/・work-queue.json 等の実行時データは .gitignore 済み。
